# 章节评论侧边栏技术方案

## 1. 结论

推荐采用“CSV 预处理 + 当前原生前端渲染”的实现路线。

现有页面是单文件原生 HTML/CSS/JS，已经具备章节正文、段评气泡、评论抽屉、段落定位、回复展开等基础结构。本期核心工作不是重建页面，而是把演示评论数据替换为真实评论索引，并补齐“按评论对象聚合、按标签筛选、按段落/标题筛选”的状态逻辑。

不建议此阶段引入 React、Vue、Tailwind、打包工具或运行时 CSV 解析库。它们会放大改造面，也不符合当前项目保持单文件页面和轻量协作的约定。

## 2. 技术路线

### 2.1 数据预处理

新增一个开发期脚本，将原始 CSV 转成前端可直接消费的结构化数据。脚本建议使用 Python 标准库 `csv/json`，不引入新依赖。

预处理脚本负责：

1. 读取 CSV。
2. 区分一级评论和二级回复。
3. 按 `段落ID` 建立评论对象。
4. 按 `顶级评论id` 将回复挂到对应一级评论。
5. 拆分 `作者视角_固定标签` 与 `作者视角_内容标签`。
6. 生成评论数量、标签数量、段落索引等前端索引。
7. 过滤空正文、孤儿回复等异常数据，并输出简要统计。

运行态页面不直接解析 CSV，避免把 56 列原始数据、转义 JSON、审核字段和 IP 等无关信息带到浏览器里。

### 2.2 运行态数据文件

有两种可选落地方式：

1. **推荐 MVP：生成 JS 数据块并内联到 `index.html`**
   保持当前单文件页面约定，生成 `var COMMENT_DATA = {...}` 形式的数据块，替换现有 `SECTION_POOL / COMMENT_TAGS / SECTION_COUNTS` 的演示数据。

2. **后续可选：独立 `data/comments.generated.json` 或 `comments.generated.js`**
   适合评论数据继续膨胀、多章节复用、或接入真实接口前的过渡。但这会改变“单文件即可运行”的当前约定，需要团队确认。

当前更建议先采用第 1 种，让页面仍然只依赖 `index.html`。

## 3. 前端数据结构

前端只保留页面需要的数据：

```js
var COMMENT_DATA = {
  chapter: {
    title: '第1章 面试',
    targetId: -1
  },
  targets: [
    {
      targetId: 0,
      targetType: 'paragraph',
      targetText: '...',
      totalCount: 114,
      mainCount: 90,
      comments: [...]
    }
  ],
  chapterComments: {
    targetId: -1,
    totalCount: 621,
    mainCount: 540,
    comments: [...]
  },
  tagCounts: [
    { name: '全部', count: 4465 },
    { name: '好评', count: 93 }
  ]
};
```

一级评论结构：

```js
{
  id: '1096574868193673217',
  targetId: 87,
  targetText: '除了各种高中教材...',
  userGuid: '3518024645',
  nickname: '3518024645',
  avatarUrl: '',
  userBadge: '',
  body: '修仙界也会传来噩耗？...',
  fixedTags: [],
  contentTags: ['睡太少/不睡觉太狠'],
  likeCount: 257,
  createdAt: '2025/1/14 23:53',
  sortValue: -1,
  replies: [...]
}
```

头像、昵称和用户标签当前 CSV 不完整。MVP 中昵称按 PRD 使用 `用户guid`，头像用 `userGuid` 哈希生成默认头像，用户标签缺失则隐藏。

## 4. 排序策略

当前 CSV 中一级评论的 `自定义排序` 全为 `-1`。结合最新 PRD 口径，建议默认排序为：

1. 有有效 `sortValue` 时，`sortValue` 越小越靠前。
2. `sortValue` 为空或 `-1` 时，按 `likeCount` 降序。
3. 点赞数相同则按原始 CSV 行号稳定排序。

这样“每段展示前 3 条”更接近作者优先看重点反馈的使用场景，也避免刷新后顺序跳动。

### 4.1 三档排序的分工（PRD §10.4）

`sortComments(list)` 只负责**单条一级评论**在列表内的排序（默认/最热/最新三个 comparator），聚合块之间的顺序由 `renderAllComments` 控制：

| 排序 | 聚合块顺序（全部评论视图） | 块内/单对象一级评论 |
|------|--------------------------|---------------------|
| default | 章评 → 段落序 → 未匹配 | sortValue 升序兜底点赞降序 |
| hot | 按 `target.totalCount`（含回复）降序；未匹配仍最后 | 点赞数降序 |
| latest | **不聚合**：拍平所有命中的一级评论按 `createdAt` 倒序 | createdAt 倒序 |

「最新」模式是对聚合模式的降级渲染：复用 `renderParagraphCommentItem` 单条卡片模板，去掉 `.cm-full-module` 外壳与 `.cm-section-link` 展开按钮；一级评论的二级回复展开行为保持不变。

切换排序 tab 后评论列表 `scrollTop = 0`（与标签筛选一致）。

### 4.2 「最新」模式的性能权衡

拍平渲染 4,465 条一级评论时 DOM 数量显著增大（每条约 15 个节点）。MVP 直接一次性渲染（实测秒级可完成），不引入虚拟列表；若后续评论量级达到数万条再考虑分页或虚拟滚动。

## 5. 前端改造点

### 5.1 替换演示数据

当前页面中这些数据需要替换或改造：

- `SECTION_COUNTS`：改为从 `COMMENT_DATA.targets[].totalCount` 得到。
- `SECTION_POOL`：移除演示池，改为真实一级评论和回复。
- `COMMENT_TAGS`：改为从 `COMMENT_DATA.tagCounts` 渲染。

### 5.2 统一状态模型

建议保留当前原生 JS 状态变量，但收敛为下面几个状态：

```js
var commentState = {
  view: 'all',              // all | target
  selectedTargetId: null,   // -1 表示章评，0+ 表示段评
  activeTag: '全部',
  sort: 'default',
  hoverTargetId: null
};
```

所有渲染函数都从这个状态读取数据，避免标签、段落、排序之间互相覆盖。

### 5.3 全部评论视图

全部评论视图按目标对象聚合：

1. 遍历正文段落顺序。
2. 过滤当前标签命中的一级评论。
3. 每个有评论的段落展示前 3 条。
4. 超过 3 条显示“查看本段 n 条评论”。
5. 最后追加章评聚合块。

二级回复不参与标签命中判断，只随父级评论展示。

### 5.4 单对象评论视图

进入单对象视图后：

1. `selectedTargetId` 记录当前段落或标题。
2. 侧边栏展示该对象下所有一级评论。
3. 默认不展示顶部标签筛选。
4. 保留“返回全部评论”入口。
5. 中间正文对应段落或标题保持高亮。

### 5.5 正文气泡

气泡计数从真实评论聚合结果读取：

1. `targetId = -1` 的计数显示在标题后。
2. `targetId >= 0` 的计数显示在对应段落后。
3. `0` 不显示。
4. 大于 `999` 显示 `999+`，`title` 属性保留真实数量。

定位正文时优先使用 `段落ID`，不要用 `评论对象` 文本反查。CSV 中评论对象文本存在空值、空格和换行差异，只适合展示和数据校验。

### 5.6 评论正文清洗 [fn=N]（PRD §9.1）

起点评论文本携带脚注标记 `[fn=N]`（样例 916 条）。清洗放在渲染层 `commentBodyHtml`：

```js
var body = escapeHtml(c.body || '');
body = body.replace(/\[fn=\d+\]/g, '');
```

- 先 escape 再正则清洗：escapeHtml 不转义 `[` `]` `=`，正则不受影响。
- CSV 与内联 `COMMENT_DATA` 保留原始文本；若日后改为上标展示，只动这一处。
- 回复正文复用同一函数，自动生效。

### 5.7 标签云折叠态选中可见（PRD §11.2.1）

列表滚动折叠标签云后，选中标签可能落在可视区之外。实现 `syncSelectedTagInView()`：折叠态下对 `.cm-tag.on` 执行 `scrollIntoView({block:'nearest'})`；触发点为标签点击切换与列表滚动引起的折叠态变化。

### 5.8 Hover 原文防误触：指针轨迹判定（PRD §13.1.1）

采用行业通行的 hover intent 方案（计时窗 + 位移阈值）：

1. `mouseenter` 记录起点坐标，启动 150ms 观察窗定时器。
2. 观察窗内 `mousemove` 累计位移（|dx|+|dy|）超过 20px 时判定为「扫过」，取消定时器、不触发滚动。
3. 观察窗自然到期且未取消时才调用 `scrollToTarget`。
4. `mouseleave` 时清除定时器与临时高亮。

模块级 `hoverIntent` 状态保存当前观察窗信息，避免多个评论对象之间残留未决定时器。

## 6. 性能判断

CSV 样例规模为 7,493 行，其中一级评论 4,465 条、二级回复 3,028 条。这个规模在浏览器端一次性载入和渲染索引没有压力。

页面实际 DOM 量也可控：

- 全部评论默认每个对象最多 3 条一级评论。
- 单段评论最大约数百条一级评论。
- 回复默认折叠，点击时才展开。

因此 MVP 不需要虚拟列表。若后续单章评论达到数万条，再考虑分页、懒加载或虚拟滚动。

## 7. 测试方案

在现有 `test/smoke-test.sh` 基础上补充断言：

1. 默认打开页面后评论侧边栏展开。
2. 标题气泡显示章评数。
3. 段落气泡数量来自真实评论数据，`0` 不显示，超过 `999` 显示 `999+`。
4. 点击段落气泡后，只展示该段落一级评论。
5. 全部评论按段落顺序聚合，章评排最后。
6. 每个聚合块最多展示 3 条一级评论，超过时显示“查看本段 n 条评论”。
7. 标签点击后真实筛选一级评论，并保持聚合顺序。
8. 二级回复默认收起，点击按钮展开。
9. hover 评论对象能滚动定位正文，但不改变当前筛选状态。
10. 右侧工具栏在侧边栏开关状态下仍贴 viewport 最右。

数据预处理脚本也需要输出并校验统计值，例如总行数、一级评论数、回复数、章评数、段评数、孤儿回复数。

## 8. 风险与处理

| 风险 | 处理 |
| --- | --- |
| CSV 字段名较长且含中文标点 | 在预处理脚本中集中声明字段映射，不在前端散落引用原始列名。 |
| `评论对象` 文本不稳定 | 定位和聚合只依赖 `段落ID`，文本只用于展示。 |
| 头像、昵称、用户标签缺失 | MVP 使用 `用户guid` 和哈希头像兜底；用户标签隐藏。 |
| `自定义排序` 全为 `-1` | 默认按点赞数降序，再按原始行号稳定兜底。 |
| 数据量继续增大 | 先保持折叠回复和聚合展示；超过数万条再引入分页或虚拟列表。 |
| 改动影响现有布局 | 保留 flex order 约束，继续用像素探针验证右侧工具栏贴边。 |

## 9. 推荐实施顺序

1. 写 CSV 预处理脚本，生成归一化评论数据和统计报告。
2. 将 `index.html` 中演示数据替换为真实数据块。
3. 改造气泡计数和标题气泡。
4. 改造全部评论视图为按段落聚合。
5. 改造单对象评论视图。
6. 接入标签真实筛选。
7. 补充 hover/点击评论对象定位。
8. 更新 smoke test 并跑通回归。

整体上，这条路线可以最大程度复用现有页面，同时把复杂度集中在“数据清洗”和“状态渲染”两处，后续切换到后端 API 也比较顺滑。
